## 目的・背景

4b までで、素材集の承認・取り下げと、チャンネルの利用の記録がデータに入るようになった。本書は、それを承認済みリスト（SanpoGuide の API-002 1.2）に載せる公開の処理と、毎日の外部の素材の確認（DM-001 M-21、ADR-002 D-22）、準拠テストの追加を決める。

**直すべき不具合**: 公開の処理は、GSI2 の `LISTED` と `REVOKED` のパーティションの項目をすべてチャンネルとして読んでいる。4b-1 から素材集も同じパーティションに入るので、素材集を 1 つ承認・取り下げると、ID のないチャンネルがリストに入り、公開の前の確かめで失敗する（まだ配備していないので、公開中のリストには影響していない）。本書の M-1 で直す。

## 方針・決定事項

| No. | 判断 | 理由 |
|---|---|---|
| M-1 | **不具合の修正**: `LISTED` は `GSI2SK` の接頭辞（`CH#`・`COL#`）で、`REVOKED` は項目の `kind` でチャンネルと素材集を分けて読む | 上の「直すべき不具合」 |
| M-2 | `packages/protocol` の型とリストの作成・確かめに、`collections[]`・`revokedCollections[]`・`channels[].media`・`resourcesSize` を足す。`format` は 1 のまま（API-002 P-12）。配列は空でも毎回書く | 古いアプリは知らない項目を無視する |
| M-3 | 素材集の項目は、素材集の `latestApproved` から作る（承認時に計算済み。DM-001 M-24）。リストに出さないもの（`submissionId`・`resourceTypes`・`externalResources`・`appStage`）は落とす。`producerChange` はチャンネルと同じく、`until` があって過ぎておらず、載せる版の素材提供者と違うときだけ載せる | API-002 P-13 |
| M-4 | チャンネルの `resourcesSize` は「自身の前もっての取得の大きさ」＋「宣言した素材集のうち、今リストに載っているものの `resourcesSize`」。`media` は「自身の素材の種類」と「その素材集の `media`」を合わせたもの（素材集の中で参照しない種類も含むので、多めに出る）。4a より前に承認されたチャンネル（`ownMedia` などがない）は、どちらも載せない | DM-001 M-24。素材集の版が変わると、次の公開で値が変わる |
| M-5 | チャンネルの `minAppVersion` は承認時の値のまま（公開のたびに計算し直さない）。D-8 で、参照している素材の種類は変わらないため | 承認時に素材集の中身まで数えている（DES-008 K-7） |
| M-6 | 公開の記録に `collectionCount`・`revokedCollectionCount` を足す | API-001 1.1 `Publication` |
| M-7 | **毎日の外部の素材の確認**（M-21）は、公開の Lambda の毎日の実行（`daily`）の、公開が終わった後に行う。公開中の素材集の `externalResources` の URL に HEAD を送り、取得できるかと大きさ（`Content-Length`）だけを確かめる。結果を素材集の `externalCheck` に書き、前回にはなかった不具合があれば、素材提供者に `collection.external_failed` を知らせる。確認の失敗は公開を失敗にしない | 公開を遅らせない・止めない |
| M-8 | **M-7 の SSRF への備え**は、機械審査（DES-007 J-6）と同じ規則を TypeScript で書く（名前を引いて内側・特別なアドレスを拒む。Node の `net.BlockList`。リダイレクトは追わない。HTTPS だけ）。同じ例（18 種類のアドレス）でテストする | 公開の Lambda は Node なので、Kotlin の実装をそのまま使えない。同じ規則を 2 か所に書くことになる（未決事項 No.1） |
| M-9 | チャンネル自身の外部の素材（`resources` の `url`）は、今回は毎日の確認に入れない（機械審査が URL の一覧を記録していないため） | D-22 は素材集の確認。チャンネル自身の分は、必要になったら機械審査の記録に足す |
| M-10 | 準拠テストに、API-002 1.2 の V-19（素材集の ID・パッケージの SHA-256 と大きさ）、V-20（チャンネルが宣言した素材集がリストにあり、版が足り、利用許諾がチャンネル提供者を含む）、V-25（`tags`・`regions`・`grants` がパッケージから計算した値と一致）を足す。V-21（`resourcesSize`・`media`）は計算の材料（外部の素材の大きさ）がリストだけでは揃わないので、今回は「`media` が正しい種類の名前だけ」「`resourcesSize` が 0 以上」の形の確認にとどめる | 任意のリストに対して流せる確認に絞る |
| M-11 | アプリのテスト用の文書（`conformance/src/app-vectors.ts`）に素材集を 1 つ足す。SanpoGuide の `ProviderDocumentsTest` は、次にベクトルを取り込むときに、管理システムが署名した素材集つきのリストで確かめられる | SanpoGuide 側は今の再署名のテストで足りている。ベクトルの取り込みは SanpoGuide のアプリの段（T-8）で行う |

## 検証の計画

| 項目 | 内容 |
|---|---|
| 公開の単体テスト（今の `api/test` の公開のテストに足す） | 素材集の承認・取り下げがあっても、チャンネルのリストに混ざらない（M-1）。`collections[]`・`revokedCollections[]` の中身、`producerChange` の載せ方、チャンネルの `resourcesSize`・`media` の足し合わせ、素材集の新しい版で次の公開から値が変わる（DV-21） |
| 外部の素材の確認 | 手元の HTTP サーバー（取得できる・404・大きさが違う・リダイレクト）、アドレスの判定（18 種類）、新しい不具合だけを知らせる、公開は失敗しない |
| 準拠テスト | 素材集つきのリスト（手元）で V-19・V-20・V-25 が通り、壊した例で落ちる |
| 本物の AWS での通しの確認 | 4a〜4c をまとめて（SSO のログインの後）: 素材集の申請 → 承認 → リストに載る → それを使うチャンネルの承認 → リストの `resourcesSize`・`media` |

## 検証結果

| 項目 | 結果 |
|---|---|
| 公開（DynamoDB Local、`api/test/collections.test.ts`） | 2 件。素材集と、それを使うチャンネルを承認して公開すると、チャンネルは 1 件だけで、`media`（自身と素材集の種類）・`resourcesSize`（自身 ＋ 素材集）・`minAppVersion` が入り、承認だけが使う項目（`appStage`・`collections`・`ownPrefetchBytes`・`ownMedia`）は出ない。素材集は `collections[]` に入り、`resourceTypes`・`externalResources` は出ない。素材集の取り下げは `revokedCollections[]` だけに入り、`revoked[]` とチャンネルには混ざらない（M-1） |
| 見つけた不具合 | M-1 に加え、4b-2 から `latestApproved` の内部の項目（`appStage` など）がチャンネルの項目にそのまま出る状態だった（公開の処理が `latestApproved` を丸ごと写していたため）。M-4 の実装で取り除き、上のテストで確かめた |
| 外部の素材の確認（`api/test/external.test.ts`） | 6 件。アドレスの判定（機械審査と同じ 18 種類を拒み、公開のアドレスを通す）、取得できる・HEAD を受け付けないサーバー（1 バイトの GET）・大きさの違い・404・時間切れ・リダイレクトを追わない、HTTPS 以外・内側に引ける名前を拒む、新しい不具合だけを知らせる、時間を超えた分は翌日 |
| 実装で見つけたこと | Node の `BlockList` は、IPv4 のアドレスを IPv6 の規則にも `::ffff:` の形で当てるため、`::ffff:0:0/96` を拒むとすべての IPv4 が拒まれた。IPv4 に写した IPv6 は文字の形で拒むようにした |
| 準拠テスト | 12 件（新しく 4 件）。この仕組みで公開した、素材集を使うチャンネルのあるリストがすべての確認に通り、V-19（パッケージの大きさの違い）・V-20（載っていない・利用許諾がない）・V-21（知らない種類）・V-25（タグ・地域の違い）で落ちる |
| SanpoGuide のアプリとの照合 | 新しいテスト用の文書（素材集つき）を SanpoGuide の `ProviderDocumentsTest` に一時的に当てた。署名の確認とリストの読み込みは通り、落ちたのは「古い文書には素材集がない」ことを確かめる 1 か所だけ（予想どおり）。SanpoGuide で文書を取り込むときに、この確認を直す |
| 全体 | TypeScript の単体テスト 133 件・型検査が合格 |
| 本物の AWS | 本物の AWS での通しの確認（2026-10-11、開発用。`tools/e2e/collections.ts`）: 外部の音声つきの素材集の機械審査が 3.5 秒で合格（HTTPS で外部の素材を読みハッシュが一致）→ 身元の確認つきで承認 → リストの `collections[]` に載り `col/` のパッケージを取得できた → それを再生するチャンネルの機械審査が素材集を `usable` と解決して 3.6 秒で合格 → 承認で利用の記録が書かれ、`used-by` に出た → リストのチャンネルに `media`（audio・text）と `resourcesSize`（6933、素材集の分）が入り、内部の項目は出なかった → 準拠テストがすべて合格（V-19〜V-25 を含む）→ 毎日の確認は、外部の素材があるあいだ不具合なし、消すと `HTTP 403` を記録し、`collection.external_failed` が通知の Lambda に届いた（開発用のテストのアカウントにはメールがないので送信は skipped）。既存の `machine-review.ts`・`review.ts` も合格（素材のないチャンネルの動きは変わらない） |

## 未決事項・リスク

| No. | 内容 | 対応 |
|---|---|---|
| 1 | SSRF の規則が Kotlin（機械審査）と TypeScript（毎日の確認）の 2 か所になる | 同じ例でテストする。どちらかを変えるときは、もう一方も変える（両方のファイルに注記する） |
| 2 | HEAD に答えないサーバー（405 など）がある | 405・501 のときは、先頭の 1 バイトだけの GET（`Range: bytes=0-0`）で取得できるかを確かめ、大きさは確かめない |
| 3 | 素材集が多くなると、毎日の確認に時間がかかる | 1 つの URL に 10 秒、全体で 5 分まで。超えたら残りは翌日 |
